一、先讲清楚三层结构

打开 WorkBuddy 任何一个专家，你看到的标签和它真正的行为之间，至少隔着两层：

专家(展示层清单)  manifest.json
   ↓ 解析
插件包(可下载单元)  bundles/<plugin>.tar.gz
   ↓ 解压
构件(agents/skills/rules/scripts/mcp/hooks)

关键结论：

  • 标签只是清单里的展示元数据，不影响执行
  • 真正决定行为的是插件包里的 agents/<name>.md（人格提示词）+ 私有 skill
  • 同名 skill 被不同专家调用时，因为外层 prompt 不同，产出形态可能天差地别

二、48 秒，装完 421 个市场专家

440 个专家里有 421 个走公开 COS 源（acc-1258344699.cos.accelerate.myqcloud.com/.../bundles/<name>.tar.gz），剩下 19 位没有公开安装包（走运营平台签名 URL），其中只有 15 位是真正的腾讯内部专属。

但"没有公开包"不等于"外部不能用" —— manifest 里有 visibility 字段：19 位里 12 位是 internal_only，真正外部可召唤的只有 4 位：AICoding 架构专家团、庄老师（企鹅教师助手）、送报报、MigraQ。剩下 15 位（贝安、阿拉丁、CPQ、哈勃、觅诊、腾讯招聘、小T、问图、甄需明等）才是腾讯内部专属，外部账号无论如何搜索都不会出现。

助理写了个 Python 脚本，并发 10 路下载全部 421 个 tar.gz，48 秒搞定，0 失败。

三、召唤 = 真安装（很多人没意识到）

很多用户以为「点击召唤」只是把专家从云端加到一个列表里，其实：

  1. 触发 ExpertPluginService.ensureDownloaded()
  2. 下载 tar.gz
  3. 解压到 plugins/<name>/
  4. 增量回写 marketplace.json
  5. 留 .downloaded_at 时间戳

也就是说，召唤一次就真实落盘一次。召唤 421 次 = 421 次网络下载 + 解压 + 写盘。这也是手工一个个点会卡住的根本原因。

绕过方式：助理在客户端代码里发现一个 explicitBundleUrl || 默认COS地址 的双源降级设计，默认地址就是上面那个公开桶，无需签名。批量脚本只是复刻了客户端的下载解压流程，但走了原始降级路径。

完整逆向过程在仓库 拆解报告/06-安装机制逆向.md，含 5 步日志取证、3 条安装通道对比、19 位无公开包专家可见性全表、7 条工程设计借鉴。

五、同标签 ≠ 同能力（L0–L4 差异模型）

我们对比了 5 组同标签专家的实际构件（标签、提示词、rules、skill、编排），得到一个四层差异模型：

层次影响典型差异
L0 标签不影响执行标签字符串完全相同
L1 人格 agent.md最主要同名 skill + 完全不同的指令链
L2 rules强约束输出格式、强制条款差异
L3 skills/mcp/scripts能力边界调用的工具集不同
L4 members 团队编排协作模式团队型专家的成员分工

一个具体例子：minimax-docx 这个 skill 在 15 个专家里都出现，文件名相同。但装载它的「ContentCreator」和「ComplianceAuditor」，外层 prompt 把它当作不同的工具使用——一个输出品牌故事，一个输出合规条款。

执行差异的四种机制：

  1. 外层 prompt 决定了 skill 输出的取舍
  2. rules 文件是硬性条款，越多越「霸总」
  3. skill 的 description 字段被模型当路由表读，写得越具体，越不容易误用
  4. 团队型专家靠 members 分工，单体专家靠单 prompt 强

九、几点反思

  • 公开 COS 源这件事本身值得点赞：愿意让数据可枚举，是生态自信的表现。但代价是所有专家提示词可被匿名下载，签名通道的防护形同虚设。
  • 19 位无公开包专家里 15 位是内部专属、外部召唤不了 是个产品问题：manifest 里躺着 internal_only 的专家，外部用户在 GUI 里看不到也搜不到，却要忍受"440 个专家"的营销数字——可见列表 ≠ 可召唤列表，而且没有提前说明。
  • 「点击召唤」的真实安装成本应该被 UI 暴露出来，否则用户会以为这是云端调用，结果发现本机硬盘涨了 1.5GB。
  • 「标签 = 能力」是错觉。同样的「数据分析」标签下，可能藏着 5 种完全不同的 prompt 范式。自查网站至少能让你看清这点。
  • 最诚实的一点：这篇文章是 WorkBuddy 助理帮我写的，包括逆向、脚本、统计和排版。我做的事是提问、验证、纠错（比如它最初把 skill 数统计成 1165，我们重算才修正为 1465）。AI 干的活可以很多，但结论要人来核。

本文与所有数据基于 2026-08-19 当天本地扫描。如果 WorkBuddy 后续更新了专家市场，欢迎提 issue 让我跟进。
